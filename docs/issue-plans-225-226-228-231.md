## #231: E2E coverage for the gift / promo checkout path

### Current state

- `src/components/gift/GiftCheckoutForm.tsx` is a react-hook-form + zod form (`src/lib/validations/gift.ts`)
  with fields `recipientEmail`, `deliveryDate` (defaults to today, `min=today`) and optional `message` (max 500).
  Submit button label: "Send this gift", "Processing gift…" while submitting. Errors render with `role="alert"`.
- It is rendered by `src/app/gift/[courseId]/page.tsx`, which loads the course with `coursesApi.get`, calls
  `giftsApi.create(...)` and on success routes to `/gift/[courseId]/confirmation?token=...&recipient=...`.
  On failure it shows a toast titled "Gift failed". If the course load fails it shows "Course not found".
- The claim side lives at `src/app/gift/claim/[token]/page.tsx` (`giftsApi.get` / `giftsApi.claim`).
- **Prerequisite problem:** `giftsApi` is imported in both gift pages but a search of `src/` finds no
  definition of it in `src/lib/api/services.ts` (only the two import sites). Before any E2E can pass,
  confirm whether it is missing on `main` (broken build or type error) or defined elsewhere. If it is
  missing, that is a separate bug and should be raised on the issue/with a maintainer first. I would
  not silently add it inside a test PR.
- "Promo code redemption" is split across places:
  - `src/components/checkout/OrderReview.tsx` has a **simulated** promo check (800 ms delay; accepts only
    `LEARN10` and `STUDENT`; flat 10% off). It does not call `promoCodesApi.validate`.
  - `src/components/instructor/PromoCodeForm.tsx` and `promo-codes-csv.ts` are the instructor-side creation
    and CSV export tooling (already unit tested under `src/components/instructor/__tests__/`).
  - `GiftCheckoutForm` itself has **no promo field**.
  The issue text mixes these, so scope needs confirming (see open questions).
- `e2e/enrollment.spec.ts` is the template: `page.route('**/api/v1/...')` mocks, `mockCourses` /
  `mockPromoCodes` from `e2e/fixtures/course.ts`. Note its promo test looks for `WELCOME20`, which the
  current `OrderReview` would reject, so I would not copy its promo assertions.

### Plan

Add `e2e/gift-checkout.spec.ts` in the style of `enrollment.spec.ts`:

1. `beforeEach`: mock `GET **/api/v1/courses/**` with a fixture course; mock the gift create endpoint
   (`POST **/api/v1/gifts`, path to be confirmed once `giftsApi` is located).
2. **Happy path:** open `/gift/<courseId>`, assert heading "Gift this course" and the price banner, fill
   recipient email and message, click "Send this gift", assert the request body (`recipientEmail`,
   `deliveryDate`, `message`) and the redirect to `/gift/<courseId>/confirmation` with `token` and
   `recipient` query params.
3. **Failure / edge cases** (at least one required; I propose three, each small):
   - Validation: submit with an empty/invalid email, assert the "valid email" alert and that no request was sent.
   - Past delivery date is rejected (`min` attribute plus zod message).
   - API error: gift create returns 500, assert the "Gift failed" toast and that the user stays on the page with
     the button re-enabled.
   - Course 404: assert "Course not found" and the "Browse courses" link.
4. **Promo path:** if maintainers confirm it belongs here, add a test through the checkout page using the codes
   the code actually accepts (`LEARN10`, `STUDENT`, plus an invalid code error). Otherwise leave promo to a
   follow-up once `OrderReview` calls the real validate endpoint.
5. Use role/label locators (`getByLabel('Recipient email')`, `getByRole('button', { name: /send this gift/i })`),
   avoid `waitForTimeout`, and add `data-testid` only where there is no accessible handle.

### Verification

- `npm run test:e2e` across chromium, firefox, webkit and both mobile projects in `playwright.config.ts`
  (the `visual` project is excluded by `grepInvert`). Run once per project to catch browser-specific date input behaviour,
  since `type="date"` fills differently in WebKit.
- `npm run lint` and `npm run format`.

### Risks

- Missing `giftsApi` (above).
- The date default uses `new Date().toISOString()` (UTC), so tests near midnight can disagree with the local
  date; build dates in the test from the same expression rather than hardcoding.
- `giftSchema` computes `today` at module load, so a long-lived page can go stale; not a test problem, but
  worth a note on the issue.

## #225: `StarRating` keyboard interaction and screen-reader announcements

### Current state (`src/components/Reviews/StarRating.tsx`)

The component already has partial support:
- A `role="radiogroup"` (`aria-label="Star rating"`) with five `<button role="radio" aria-checked>` stars,
  roving `tabIndex` (`focusIdx`), and a key handler for arrows, Home, End, Space and Enter.

Gaps found:
1. **Arrow keys move focus but do not change the value.** `focusStar()` only focuses; selection happens only on
   Space/Enter/click. For a radiogroup the expected behaviour (and the issue's wording: "arrow keys to change
   value") is that arrows select. The existing tests contradict the component: `StarRating.test.tsx`
   expects `ArrowRight` to make "2 stars" `aria-checked="true"`, and the Rating Breakdown / average tests look
   for things the component does not render (`★` labels, `5.0` text). So several current tests likely fail.
   First step is running `npx vitest run src/components/Reviews/StarRating.test.tsx` to record the baseline.
2. **Nothing is announced.** The pill text ("4 — Good") and the average block are plain text with no
   `aria-live`, so a screen reader user hears nothing when the value changes. The decorative dot is not hidden.
3. **Toggle-off on re-select** (`handleStarClick` sets 0 when re-clicking the same star) is unusual for radios
   and conflicts with arrow selection (arrowing onto the selected star must not clear it).
4. **Focus ring** is driven by `focusIdx` rather than `:focus-visible`, so the outline shows on mouse click and
   stays after blur.
5. **Breakdown rows** are `div role="button" tabIndex=0` with a click handler but no key handler, so Enter/Space
   do nothing (a jsx-a11y violation). No visible focus style.
6. Roving tabindex starts on star 1 even when a rating exists; it should start on the checked star.

### Plan

1. Reproduce: keyboard only (Tab into group, arrows, Space/Enter), plus NVDA/VoiceOver; record findings in the PR.
2. Make arrows select: `ArrowRight/Up` -> `setSel(min(5, i+1))` and focus; `ArrowLeft/Down` -> `max(1, i-1)`;
   Home/End select 1/5. Keep Space/Enter selecting the focused star; keep an explicit "Clear" button instead of
   toggle-off-by-click (confirm with maintainers since this changes behaviour).
3. Roving tabindex follows the selected star (fall back to star 1 when none).
4. Add a visually hidden `role="status"` / `aria-live="polite"` region that announces "Rating: 4 of 5, Good"
   (and "Rating cleared"). Hide the decorative pill dot with `aria-hidden`.
5. Use `focus-visible` styling instead of the always-on `focusIdx` outline.
6. Give breakdown rows real `<button>` elements (or add Enter/Space handlers) with a label such as "Filter to 4 stars, 28%".
7. Tests (`StarRating.test.tsx`, using `userEvent`): arrow keys change `aria-checked`, bounds at 1 and 5, Home/End,
   Space/Enter, roving tabindex, live-region text, breakdown row keyboard activation. Fix or delete the tests that
   assert content the component never rendered. Add an `axe` check: `jest-axe`/`vitest-axe` is not a dependency
   today, so propose adding `vitest-axe` as a devDependency and call this out in the PR.

### Verification

Manual keyboard-only pass plus NVDA/VoiceOver notes; `npm run test`, `npm run lint` (jsx-a11y), update
`StarRating.stories.tsx` if the visible states change.

## #226: `FilterDrawer` focus management

### Current state (`src/components/search/FilterDrawer.tsx`)

Already present: `role="dialog"`, `aria-modal`, `aria-label`, Escape closes, body scroll lock, focus moves to the
panel on open. The comment in the code says "focus trap entry" but there is no trap.

Gaps found:
1. **No focus trap.** Tab can leave the panel into the page behind the backdrop.
2. **Focus is not restored** to the button that opened the drawer when it closes.
3. **The closed drawer stays in the DOM.** The wrapper uses `aria-hidden={!open}` but the panel's buttons and the
   filter controls remain focusable (just translated off-screen), which is a known a11y failure (focusable
   content inside `aria-hidden`). It should be `inert`, `visibility: hidden`, or not rendered when closed.
4. **Backdrop is a clickable `div`** (fine for mouse; keyboard users have Escape and the close button).
5. The Escape listener is on `document` and effect deps include `onClose`, which `search/page.tsx` passes as a new
   inline arrow on each render. The effect re-runs every render, re-running `panelRef.current?.focus()` and
   stealing focus from whatever the user was interacting with inside the drawer. Needs a ref for `onClose`.
6. Trigger button lives in `src/app/search/page.tsx` (`showFilters` state); the drawer has no handle to it.

### Plan

1. Reproduce with keyboard: open drawer, Tab repeatedly, note escape to page; close and note focus lost to `<body>`.
2. Store `document.activeElement` when `open` becomes true; on close restore focus to it (guard that it is still
   connected). This keeps the component API unchanged (no trigger ref prop needed).
3. Implement a small trap: on Tab / Shift+Tab, wrap between the first and last focusable elements inside the panel.
   Prefer a small local hook (`useFocusTrap`) unless the repo already has one (check `src/lib/hooks` and
   `components/ui` modals first and reuse it if present).
4. Stabilise the effect: keep `onClose` in a ref so the open/close effect depends only on `open`, and focus the
   panel (or the first control) exactly once per open.
5. Make the closed state inert: apply `inert` (React 18 needs the attribute handled, so use `ref` or
   `visibility: hidden` with the existing transition delayed) so hidden controls leave the tab order.
6. Tests (`FilterDrawer.test.tsx`, new): focus moves in on open; Tab/Shift+Tab wrap; Escape closes; focus returns
   to the opener; closed drawer controls are not tabbable; axe has no violations when open. Mock `useSearchStore`
   as other component tests do.

### Verification

Keyboard-only on a mobile viewport (the drawer is `lg:hidden`), NVDA/VoiceOver check that the background is not
reachable, `npm run test`, lint, format.

## #228: `NotificationDropdown` keyboard navigation

### Current state (`src/components/notifications/NotificationDropdown.tsx`)

Already present: trigger with `aria-expanded` and `aria-haspopup`, Escape closes and returns focus to the bell,
outside click closes, rows are real `<button>`s with labels.

Gaps found:
1. **No arrow-key navigation.** Rows are only reachable by Tab; Up/Down/Home/End do nothing.
2. **Focus does not move into the panel on open**; keyboard users must Tab through the page to find it.
3. **Role mismatch:** the panel is `role="dialog"` but trigger has `aria-haspopup="true"` (which means `menu`).
   Notifications are a disclosure with actionable items, not an ARIA menu; mixing the two misleads screen readers.
4. **Escape handler is global** and only guards on `open`, so it also fires when focus is elsewhere; fine, but it
   should only refocus the trigger when focus was inside the panel.
5. **Focus loss on tab-out:** Tab past "View all notifications" leaves the panel open (no close on focus leaving).
6. The unread count badge is `aria-hidden` but the trigger label includes it. That is fine, and should be kept.
7. Group sections are `<section aria-label>` without list semantics.

### Plan

1. Reproduce: keyboard-only and screen-reader pass; record behaviour.
2. Decide the pattern with the issue ("standard disclosure-widget pattern"): keep it a disclosure, so change
   `aria-haspopup="true"` to `aria-controls` pointing at the panel id (drop `aria-haspopup`), keep `role="dialog"`
   non-modal with a label, or switch the panel to a plain region. Confirm on the issue before implementing.
3. On open, move focus to the first row (or the panel heading if there are no rows). When rows load later
   (loading state), focus the first row once loaded.
4. Add `onKeyDown` on the list container: ArrowDown/ArrowUp move between rows (wrapping or clamped, pick one and
   document it), Home/End jump to first/last. Rows plus "Mark all read" and the footer link form the ordered
   set; use a query for `[data-notification-row]` or manage refs.
5. Escape closes and refocuses the bell only if focus is within the container.
6. Close on focus leaving the container (`onBlur` with `relatedTarget` check) so Tab out does not leave an orphaned
   open panel.
7. Tests (`NotificationDropdown.test.tsx`, new; mock `useNotificationStore` and `next/navigation`): opens with Enter/Space,
   focus enters panel, ArrowDown/Up/Home/End, Escape closes and restores focus, aria attributes, axe check.

### Verification

Keyboard-only run through the header on desktop widths, screen reader pass, `npm run test`, lint, format.
